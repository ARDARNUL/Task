# Отзывы Яндекс.Карт

Сервис для работы с отзывами организаций на Яндекс.Картах: подключение карточки по ссылке, парсинг отзывов, рейтинг, счётчики и постраничный просмотр в веб-интерфейсе.

Тестовое задание. Реализовано как SPA на Vue 3 + API на Laravel 13, парсинг — через headless-браузер (Playwright) в отдельном Docker-сервисе.

## Стек

## Как это работает

```
┌──────────────────────┐      HTTP       ┌──────────────────────┐      CDP      ┌────────────┐
│  Laravel (app)       │ ──────────────► │  browser (Node.js)   │ ────────────► │  Chromium  │
│  + queue worker      │ ◄────────────── │  Playwright :3000    │ ◄──────────── │  (headless)│
│  + MySQL + Redis     │      JSON       │                      │      DOM      └─────┬──────┘
└──────────┬───────────┘                 └──────────────────────┘                    │
           │                                                                         │
           │ HTTP                                                                    │ HTTPS
           ▼                                                                         ▼
┌──────────────────────┐                                              ┌──────────────────────┐
│  Vue 3 SPA (в браузере)                                             │  yandex.ru/maps      │
└──────────────────────┘                                              └──────────────────────┘
```

Ключевая идея: **PHP-приложение не ходит напрямую на yandex.ru**. Вместо этого оно обращается к отдельному сервису `browser`, который запускает headless Chromium, открывает карточку организации как настоящий пользователь, скроллит отзывы и перехватывает XHR-ответы. Это единственный надёжный способ обойти защиту от ботов и динамическую подгрузку отзывов.

### Поток данных

1. Пользователь вставляет ссылку на карточку организации в Яндекс.Картах.
2. Laravel валидирует URL, создаёт запись в `organizations` со статусом `pending`, кладёт `ParseOrganizationJob` в очередь Redis и сразу возвращает `202 Accepted`.
3. Очередь (сервис `queue`) подхватывает джобу, дёргает `YandexMapsParser`.
4. Парсер POST-запросом отправляет URL в `http://browser:3000/parse`.
5. Node.js-сервис через Playwright:
   - открывает карточку организации (`/maps/org/.../reviews/`);
   - вытаскивает данные организации (название, адрес, рейтинг, счётчики) из `<script class="state-view">` в HTML карточки;
   - скроллит блок отзывов, перехватывая XHR-запросы к `/maps/api/business/fetchReviews`;
   - когда страница перестаёт отдавать новые отзывы, открывает **новую сессию браузера** и повторяет — так обходится лимит Яндекса на ~11 страниц за одну сессию;
   - собирает все уникальные отзывы (по `reviewId`) и возвращает JSON.
6. Laravel получает JSON, валидирует структуру, кладёт данные в DTO (`OrganizationData`, `ReviewData`).
7. `OrganizationSynchronizer` в одной транзакции обновляет организацию и делает `upsert` отзывов по ключу `(organization_id, external_id)`.
8. Запись о прогоне сохраняется в `parse_runs` (статус, счётчик отзывов, snapshot рейтинга, время начала/окончания).
9. Фронт параллельно поллит `GET /api/organizations` каждые 3 секунды и показывает статус парсинга (`В очереди` → `Парсинг…` → `Готово`).

# Дополнительные требования — ответы

## 1. Устойчивость к смене разметки

Яндекс регулярно меняет вёрстку и внутренние API. Парсер должен уметь обнаруживать, что источник изменился, и сообщать об этом, а не молча возвращать пустоту.

**Как это реализовано:**

- **Проверка структуры ответа.** После получения JSON от browser-сервиса `YandexMapsParser` проверяет: есть ли в ответе имя организации, рейтинг или хотя бы один отзыв. Если всё пусто — бросается `LayoutChangedException` (наследник `ParserException`).
- **Отдельный статус.** В enum `ParseStatus` есть значение `layout_changed`, которое отличается от общей ошибки `failed`. Организация с таким статусом подсвечивается на фронте **жёлтым** бейджем «Разметка изменилась», чтобы это было видно в UI и не смешивалось с транзиентными сбоями.
- **Без ретраев.** `ParseOrganizationJob::shouldRetry()` возвращает `false` для `LayoutChangedException` — нет смысла долбить Яндекс, если структура изменилась, надо чинить парсер.
- **Журнал прогонов.** Каждый запуск пишется в `parse_runs` со статусом, текстом ошибки и snapshot'ом метрик. По истории видно, когда парсер начал отдавать пустоту.
- **Дополнительный детектор в Node.js.** Если `fetchFirstPage` не находит `<script class="state-view">` в HTML, это тоже логируется как аномалия и попадает в ответ как `ok: false, error: "state-view not found"`.

**Что бы доделал:** golden-fixture тесты — сохранять реальные ответы Яндекса в репозиторий и прогонять парсер против них в CI. Это ловит смену разметки до того, как её увидят пользователи.

## 2. Обоснование подхода к парсингу

Рассматривались три подхода.

### A. Headless-браузер (Playwright + Chromium) — выбран

**Плюсы:**
- Проходит защиту от ботов: TLS-фингерпринт настоящего Chrome, JS выполняется, куки и сессии работают штатно.
- Не нужно разбирать эфемерные токены (`csrfToken`, `reqId`, `sessionId`), которые Яндекс меняет на каждый запрос и подписывает HMAC.
- Работает со сменой деталей API: если URL внутренних XHR поменяется, но вёрстка останется — достаточно поменять фильтр по URL в `page.on('response')`.
- Стабильнее к защите через `s` (подпись в query string), которую невозможно подделать без реверса JS-рантайма Яндекса.

**Минусы:**
- Тяжелее по CPU/RAM: контейнер с Chromium занимает ~500 МБ RAM.
- Медленнее: один парсинг — 2–4 минуты.
- Плохо масштабируется на десятки организаций одновременно.

### B. Прямые HTTP-запросы к внутреннему JSON API — отклонён

Мы проверили этот путь на этапе прототипирования. Endpoint `https://yandex.ru/maps/api/business/fetchReviews` отдаёт отзывы в JSON, но:

- требует `csrfToken`, который меняется после **каждого** запроса;
- требует `sessionId`, `reqId` и поле `s` — подпись, которую формирует JS-код карточки;
- с прямыми запросами через PHP/Guzzle сервер отвечает `200 OK` и... пустым JSON'ом без данных (`reviews: []`). То есть Яндекс **валидирует подпись** и молча отдаёт пустоту вместо ошибки.

Без реверса клиентского JS (или использования `curl-impersonate`) этот путь не работает. Для тестового это было бы неоправданно большой тратой времени и крайне хрупким решением.

**Плюсы (если бы работало):** быстрее, легче, легко масштабируется на 50 филиалов.
**Минусы:** критично зависит от внутренней кухни Яндекса, ломается при любом изменении токенов или подписи.

### C. PHP + php-curl с эмуляцией TLS-фингерпринта (`curl-impersonate`) — не выбран, но рассмотрен

Это компромисс между A и B: те же прямые HTTP-запросы, но через пропатченный curl, который эмулирует TLS-стек Chrome. Работает быстрее headless и проходит защиту. Но:

- в PHP это делается только через `proc_open` и внешний бинарник (теряется Laravel HTTP-клиент);
- сборка `curl-impersonate` в образ — отдельная головная боль;
- всё равно придётся реверсить `s`, если Яндекс его проверяет.

**Вывод:** для тестового задания выбран **A** (headless). Это самый предсказуемый путь, который не зависит от изменений в токенах. Если проект пойдёт в прод с 50 филиалами — имеет смысл рассмотреть **C**.

## 3. Масштаб и фоновая обработка

Парсинг **не выполняется синхронно внутри HTTP-запроса**. Всё вынесено в очередь:

- **Очередь:** Redis (`QUEUE_CONNECTION=redis`).
- **Отдельный контейнер** `queue` держит воркер (`php artisan queue:work`).
- **Джоба:** `ParseOrganizationJob` — реализует `ShouldQueue`.
- **Таймаут:** 600 секунд — запас на медленный парсинг карточки с 600+ отзывами.
- **Повторы:** до 5 попыток с экспоненциальным бэкоффом `[10, 30, 60, 120, 300]` секунд. При смене разметки (`LayoutChangedException`) — **без ретраев**.
- **Индикация прогресса:** фронт каждые 3 секунды поллит `GET /api/organizations`, пока есть организации со статусом `pending` или `running`.
- **Журнал:** каждый запуск сохраняется в `parse_runs` со статусом, количеством найденных отзывов, ошибкой и snapshot'ом метрик.

**Что бы добавил при 50 филиалах:**

- **`Bus::batch()`** — для одновременного парсинга нескольких организаций с единым batch-прогрессом.
- **Отдельные очереди** — `parsing` (тяжёлые джобы) отделить от `default`, чтобы они не блокировали мелкие задачи.
- **Горизонтальное масштабирование воркеров** — несколько контейнеров `queue`, слушающих одну очередь.
- **Rate limiting между джобами** — через `RateLimiter::for('yandex-parsing')`, чтобы не спамить Яндекс 50 запросами одновременно.
- **Планировщик** (`php artisan schedule:work`) — ежедневный перезапуск парсинга по cron.

## 4. Анти-бан на объёме

Яндекс активно защищается от ботов. Даже с headless-браузером есть ограничения и нужны меры предосторожности.

**Что уже реализовано:**

- **Новые браузер-сессии.** Яндекс даёт за один заход ~11 страниц по 50 отзывов (~550 записей). Когда лимит достигнут — сервис закрывает контекст и открывает новый. Каждая сессия — чистые куки, чистый реестр, новый запрос к Яндексу как «нового пользователя». За 2–3 сессии собираем все доступные ~600 отзывов.
- **Задержки между скроллами.** `waitForTimeout(3000)` после каждого скролла — не выглядим как автозагрузчик.
- **Паузы между сессиями.** 2–3 секунды между заходами.
- **Реалистичный User-Agent и заголовки.** Актуальная версия Chrome, `Accept-Language: ru-RU`.
- **Отключение AutomationControlled.** Флаг `--disable-blink-features=AutomationControlled` убирает самый очевидный признак автоматизации.
- **Стелки-инъекция.** В `page.addInitScript` переопределяются `navigator.webdriver`, `navigator.plugins`, `navigator.languages`, `window.chrome`.

**Что добавил бы в прод:**

- **Ротация прокси.** Набор HTTP/SOCKS5-прокси, каждому парсингу — свой. Это снимает лимит по IP и позволяет параллелить.
- **Ротация User-Agent.** Сейчас UA фиксирован, но легко расширить до пула.
- **Обработка капчи.** Если Яндекс отдаёт `smartcaptcha` — джоба помечается как `failed` с текстом «Требуется капча», алерт в UI. В идеале — интеграция с сервисом решения капчи, но для тестового это оверкилл.
- **Circuit breaker.** Если N парсингов подряд падают — ставим глобальную паузу на час (`Cache::put('parser:paused', true, 3600)`), джоба заканчивается без ретраев.
- **Ограничение частоты.** `RateLimiter` — максимум 1 парсинг в 30 секунд на инстанс.
- **Мониторинг.** Алерты на всплеск `failed` в `parse_runs` — сигнал, что что-то меняется в защите Яндекса.

## 5. Идемпотентность и история изменений

**Идемпотентность.**

Уникальный ключ в таблице `reviews` — `(organization_id, external_id)`, где `external_id` — это `reviewId` из Яндекса. Запись идёт через `Review::upsert()`, поэтому:

- повторный парсинг **не создаёт дубли**;
- существующие отзывы **обновляются** (текст, рейтинг, `last_seen_at`);
- `first_seen_at` **не перезаписывается** — по нему видно, что отзыв «старый», а что появился после последнего парсинга.

То же для организаций: `Organization::updateOrCreate()` по `(user_id, yandex_url)`.

**История изменений.**

- **`parse_runs`** — таблица-журнал. На каждый запуск: статус, количество найденных отзывов, `snapshot` (рейтинг, счётчики оценок и отзывов, сколько собрано), ошибка, время начала и окончания. По `parse_runs` можно отследить, как менялся рейтинг и счётчики во времени.
- **`reviews.raw`** — полный JSON-объект отзыва из Яндекса. Если нужно узнать, как выглядел отзыв до правок (например, `businessComment` был добавлен позже), — данные сохранены.
- **`first_seen_at` / `last_seen_at`** — позволяют понять, обновлялся ли отзыв после первого появления.

**Что бы доделал:**

- **Отдельная таблица `review_snapshots`** — при каждом парсинге писать diff по каждому отзыву: что изменилось (текст, рейтинг, добавился ответ компании). Тогда можно показать пользователю «Отзыв отредактирован 12 мая 2026».
- **Версионирование `raw`** — стек последних N версий объекта отзыва.
- **Diff на уровне организации** — «рейтинг упал с 4.7 до 4.4 за месяц», визуализация на графике.
